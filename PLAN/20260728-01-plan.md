- 本文中的数据契约、公共 API、默认 tick 参数、生命周期与验收条件均为规范性内容；示例字段若与文字规则冲突，以同节文字规则为准，并应在 Phase 0 冻结契约时消除歧义。

## Summary

- 删除现有“独立攻速计时＋技能冷却自动触发”的伪实时战斗，改为确定性、整数 tick、固定逻辑步长的 MMO 风格自动战斗时间轴；它不是旧伪实时模型，也不是等待玩家输入的严格回合制。
- 战斗技能、走位和机制处理完全由 AI 执行；玩家保留地图探索、WASD/点地、优先目标、撤离、技能构筑和战术策略配置，不提供手动技能热栏。
- 首期正式玩法仍为单玩家角色、永久单职业；底层真实支持多 Actor、四人轻型队伍、八人扩展队伍、阵营、控制器、动态关系、治疗、威胁、召唤与易主。
- 普通遭遇包含 1–3 个同编组敌人；Boss 支持施法、预警、打断、阶段转换和有限增援，不再以旧 1v1 接敌作为系统边界。
- 内容采用“内容包注册 → 分阶段校验/编译 → CompiledActorBlueprint → ActorRecord → ActorInstance → EncounterInstance”的分层模型。
- 5 个职业建立独立资源、基础行动套件、轮转与 AI；现有 30 个技能 ID 保留为可投资 Talent，其中主动 Talent 可授予或强化 Action。
- 24 个怪物（16 个普通怪＋8 个 Boss）全部获得正式战斗机制；普通怪、Boss、召唤物和未来同伴共用 Actor、Ability、Status、Relation 和 Effect 规则。
- 在线战斗、技术演示、战力评估和离线摘要复用同一套编译内容与战斗规则；长时间离线仍使用缓存摘要，不逐 tick 模拟全部时长。
- 五职业宏观首通时间、收益与死亡曲线相对旧确定性基线控制在 ±10%；不要求单场旧 TTK 或旧出手节奏等价。
- 这是单机挂机 RPG 的确定性自动战斗系统，不包含在线多人、服务器同步、网络账号或 MMO 操作负担。

参考方向：

- BG3：职业、子职、种族、物品、法术和能力的组合式内容表达，而非复制其回合制。[BG3 官方 Modding Toolkit 概览](https://baldursgate3.game/news/community-update-28-closed-beta_119)
- FF14：Action、Trait、Combo、Job Gauge、职责、队伍、施法进度和敌意结构，而非复制其具体数值。[FF14 职业指南](https://na.finalfantasyxiv.com/jobguide/battle/)、[FF14 队伍说明](https://na.finalfantasyxiv.com/game_manual/pp/)、[FF14 游戏界面](https://na.finalfantasyxiv.com/game_manual/view/)
- D&D：怪物 Traits、Actions、Reactions 和特殊行动的清晰能力分区。[D&D 怪物卡说明](https://www.dndbeyond.com/sources/dnd/br-2024/how-to-use-a-monster)

## Architecture boundaries

### 1. 五层 Actor 模型

1. `ActorArchetypeCard`：作者编写的内容定义，描述身份、表现、身体、基础阵营、基础属性和固有能力。
2. `ClassCard / TalentCard / LoadoutCard / TraitCard`：可组合覆盖层，分别描述职业、技能投资、装备与固有机制。
3. `CompiledActorBlueprint`：内容编译器解析引用、默认值、公式和索引后的深冻结结果，不进入存档。
4. `ActorRecord`：存档中的长期成长记录，只保存稳定 ID、等级、技能投资、装备、永久升级和允许持久化的资源。
5. `ActorInstance`：当前世界中的运行时实体；战斗临时状态由组件持有，退出 encounter 后按规则清理。

角色卡和怪物卡是同一底层模型的不同 Inspector 视图，不建立两套运行时对象。

### 2. 聚合根与职责

- `Game.content`：内容收集、校验、编译、审计和只读查询。
- `Game.roster`：持久 ActorRecord、主角色和队伍配置。
- `Game.actors`：世界 ActorInstance 的生成、查询、销毁和快照。
- `Game.parties`：长期或临时队伍成员关系，不决定敌我。
- `Game.relations`：Actor、encounter team、faction 的动态关系解析。
- `Game.encounters`：战斗参与者、team、时间轴、RNG、威胁、预警、奖励预算和胜负，是战斗聚合根。
- `Game.combat`：行动校验、Effect/Status 结算和结构化事件，不负责世界刷怪、寻路、经济入账或 UI。
- `Game.combatAI`：只产生行动、移动和战术意图；世界与 combat 系统负责合法执行。
- `Game.combatEstimator`：调用同一编译内容、AI 和无渲染战斗规则生成摘要。

### 3. 不可跨越的边界

- `category`、`rank`、sprite 或文件来源不得用于判断敌我、可攻击性或控制权。
- `controllerId` 与 faction、team、party 解耦。
- Actor 不得通过 getter 直接绑定 `Game.state.player`。
- 威胁、encounter 临时关系、战斗 RNG 和奖励预算不得存放在 ActorCard、ActorRecord 或全局单例中。
- 渲染帧率、Canvas 动画、弹道表现和 DOM 生命周期不得影响战斗结果。
- 内容定义禁止内联函数、`eval` 和未注册脚本回调；特殊逻辑必须引用受控 handler ID。
- 正式内容、技术演示和离线估值不得维护相互独立的技能或怪物规则副本。

### 4. 三类入口与统一 Actor 原则

“注册”“入册”和“生成”必须明确区分：

| 阶段 | 唯一入口 | 职责 |
|---|---|---|
| 内容注册 | `Game.content.registerPack(pack)` | 收集作者编写的 Actor、Ability、Status、AI、Encounter 等稳定内容定义 |
| 长期入册 | `Game.roster.createRecord(spec)` | 创建需要进入存档的玩家或未来持久同伴 ActorRecord |
| 运行时生成 | `Game.actors.spawn(spec)` | 生成所有玩家、怪物、NPC、同伴、召唤物和可战斗物件的 ActorInstance |

- 不建立 `PlayerActor`、`MonsterActor`、`NpcActor` 三套运行时类、注册表或生成管线。
- 类型专用作者工具只能是无状态薄封装，例如 `defineMonsterArchetype()` 只补作者默认值并返回普通 `ActorArchetypeCard`；它不得绕过 schema、Pack、引用编译或审计。
- `Game.actors.spawn()` 不自动创建 ActorRecord，也不默认加入 encounter；持久入册和 encounter join 必须由调用者显式请求。
- `despawn()` 只销毁运行时实例，不删除 ActorRecord、内容定义或已结算的经济结果。
- 玩家、怪物和 NPC 的敌我、控制权、可攻击性、奖励与交互能力均由 faction、team、relation、controller 和实际组件决定，不由类型名决定。

### 5. NPC、可战斗物件与 world prop 边界

- `category` 允许 `player | monster | npc | companion | summon | object`，只用于内容目录、Inspector 和作者筛选。
- 具备身份、Transform、表现、动态关系、控制器或角色型交互锚点的实体使用 Actor；商人、剧情人物和可能转为敌对的中立角色属于 NPC Actor。
- 纯装饰、采集点、宝箱、地面掉落和没有 Actor 生命周期的交易区域继续使用 world prop，不为“统一”而强行 Actor 化。
- `object` 仅表示需要 Actor 生命周期、关系或战斗结算的可选中/可破坏物件，不等同于所有世界物件。
- ActorInstance 采用能力驱动的可选组件；非战斗 NPC 可以没有 `vitals`、`actionState`、`cooldowns` 和战斗 AI。combat、targeting、UI 和 Inspector 必须先检查组件能力。
- 本版本不实现完整 NPC 对话、日程或好感系统；首次出现真实消费者时再增加可校验的 InteractionProfile，不提前堆放无消费者字段。

## Public APIs and data contracts

### 1. 内容包、受控规则与编译

统一内容入口：

```js
Game.content.registerPack({
  id: 'core.combat',
  version: '2.0.0',
  schemaVersion: 1,
  requires: [
    { id: 'core.stats', range: '^1.0.0' }
  ],
  definitions: {
    stat: [],
    statProfile: [],
    damageType: [],
    resistanceProfile: [],
    resource: [],
    resourceProfile: [],
    faction: [],
    combatRules: [],
    renderProfile: [],
    actorArchetype: [],
    class: [],
    equipmentProfile: [],
    talentTree: [],
    talent: [],
    ability: [],
    trait: [],
    status: [],
    aiProfile: [],
    tacticsProfile: [],
    evaluationProfile: [],
    rewardProfile: [],
    encounterProfile: []
  }
});

Game.rules.registerHandler('encounterPhase', {
  id: 'core.phase.standard-v1',
  version: 1,
  deterministic: true,
  fn: handler
});

Game.content.finalize({ strict: true });
Game.content.get(type, id);
Game.content.all(type);
Game.content.has(type, id);
Game.content.audit();
Game.content.fingerprint();
```

编译阶段固定为：

`收集 → Pack 依赖校验 → 结构校验 → 默认值归一 → 引用图解析 → 语义校验 → 公式/索引编译 → 内容指纹 → 深冻结`

要求：

- 注册阶段只收集定义，允许跨文件和加载顺序无关的引用；`finalize()` 在新档、读档或技术演示启动前只执行一次。
- 校验稳定 ID、Pack 版本、schema 版本、重复项、循环引用、非法覆盖、i18n、资产、公式、handler 版本和区域/遭遇映射。
- 每个编译结果保留 `sourcePackId/sourceFile` 诊断元数据，但不污染内容业务字段。
- 内容包不得静默覆盖定义；扩展包必须显式声明 `patch` 或 `replace`，核心内容默认不可替换。
- 数值使用常量、曲线或命名公式参数；公式执行器不得使用字符串 `eval`。
- handler 由引擎代码预注册，内容卡只引用 handler ID；handler 必须声明版本、确定性和允许访问的上下文。
- 生产环境发现无效核心内容时停留在标题页并显示本地化诊断，不加载或覆盖存档；测试和开发模式直接失败。
- `Game.reg.get/all/ids/has` 暂作为只读兼容门面。
- 旧 `Game.register()` 仅在 `finalize()` 前作为迁移适配器，必须经过相同校验；新内容禁止继续使用。
- 新定义优先使用类型内可读稳定 ID；现有职业、技能、怪物、区域和资产 ID 保持不变。

### 2. 内容目录、Pack 粒度与统一加载清单

目标目录：

```text
js/

    schemas.js
    compiler.js
    audit.js
    rules.js
  systems/actors/
    actors.js
    roster.js
    parties.js
    relations.js
  data/packs/
    rules/
    jobs/
      fighter.js
      rogue.js
      mage.js
      cleric.js
      ranger.js
    regions/
      grassland.js
      forest.js
      mine.js
      graveyard.js
      snowpass.js
      lavacave.js
      skyruins.js
      darkcastle.js
    world/
      camp-npcs.js
docs/content-authoring/
  adding-actor.md
  actor-schema.md
```

- 内容按纵向功能 Pack 组织，而不是为 player、monster、NPC 建立互不相干的运行时目录。一个区域 Pack 可以共同拥有其 ActorArchetype、Ability、Status、AI、Reward 和 EncounterProfile，避免新增单位时跨大量文件散弹式修改。
- 职业 Pack 共同注册职业卡、资源、基础 Action、Trait、Talent、AI/Tactics 与表现引用；区域 Pack 共同注册怪物、Boss 和遭遇内容；world Pack 保存跨区域 NPC 或世界角色内容。
- Pack 文件只能声明数据和引用，不能在加载时生成 Actor、修改存档或启动 encounter。
- 正式游戏、Actor / Combat Lab、其他技术演示和 Node 审计必须复用同一份内容加载清单或确定性生成产物，不允许各 HTML 维护不同的 Pack 列表。
- 加载清单必须兼容普通 `<script>` 与 `file://`；如采用生成产物，源 Pack 仍是唯一作者来源，生成脚本必须确定性、可审计并纳入测试。
- 新增 Pack 时只允许修改内容清单、内容数据、i18n、资产和必要测试；常规新增单位不得修改 combat、world、renderer 或 UI 业务分支。

### 3. ActorArchetypeCard

```js
{
  id,
  schemaVersion,
  category,
  rank,
  identity: {
    nameKey,
    descKey,
    loreKey
  },
  presentation: {
    spriteId,

    scale,
    renderProfileId
  },
  body: {
    size,
    collisionRadius,
    movementTypes
  },
  tags,
  defaultFactionId,
  statProfileId,
  resourceProfileIds,

  resistanceProfileId,

```

- `category` 只表示 player、monster、npc、companion、summon、object 等内容类别。
- 玩家使用通用 `adventurer` archetype 叠加 ClassCard、ActorRecord 和 Loadout。
- 普通怪、Boss、守门精英和召唤物使用相同 archetype schema，通过 rank、traits、abilities、AI 和 encounter 规则形成差异。
- 非战斗 NPC 可省略战斗专属 profile；可选组件以显式 profile/trait 引用表达，不在 card 中预留大量空字段。

```js
  traitIds,
```

```js
{
  id,
  schemaVersion,

```

- ClassCard 描述可附着职业，不充当完整角色。

- Loadout 引用装备 UID、锁槽和未来能力配置，不复制物品定义。

### 5. CompiledActorBlueprint、ActorRecord、SpawnSpec 与 ActorInstance

`CompiledActorBlueprint` 由编译器生成：

```js
{
  key,
  archetypeId,
  classId,
  resolvedTags,
  resolvedProfiles,
  resolvedAbilityGrants,
  resolvedTraits,
  sourceFingerprint
}
```

- `key` 由 `archetypeId + classId + 其他允许参与编译的稳定覆盖层 + content fingerprint` 确定性派生，只用于运行时缓存和诊断，不进入存档。
- 通用 `adventurer` 与五个 ClassCard 形成不同 Blueprint，但 ActorRecord 仍只保存稳定 `archetypeId` 和 `classId`。
- Talent rank、装备 UID、临时状态和 encounter 覆盖不改变内容定义身份；它们由 ActorRecord、Loadout、ModifierLedger 或 encounter 上下文在实例化时应用。

持久 `ActorRecord`：

```js
{
  id,
  archetypeId,
  classId,
  level,
  exp,
  skillPoints,
  talentRanks,
  permanentUpgrades,
  persistentResources: {
    hp
  },
  loadout: {
    equipment,
    lockedSlots
  }
}
```

运行时 `SpawnSpec`：

```js
{
  instanceId,
  archetypeId,
  actorRecordId,
  level,
  tier,
  transform: {
    x,
    y,
    direction
  },
  partyId,
  teamId,
  factionId,
  controllerId,
  encounterId,
  spawnSource: {
    kind,
    sourceId,
    sequence
  }
}
```

- `actorRecordId` 存在时，archetype、class、等级、Talent、Loadout 和持久资源以 ActorRecord 为准；冲突覆盖必须拒绝，不能静默选择一方。
- 无 ActorRecord 的怪物、NPC 和召唤物必须提供 `archetypeId`；level/tier、阵营、控制器和位置由 spawn context 或编译默认值解析。
- `instanceId` 在正式世界中由 actors allocator 生成，在 encounter 内由 `encounterId + spawn sequence` 确定性生成；禁止使用时间戳、无 seed 随机数或对象遍历顺序生成影响战斗排序的 ID。
- `spawnSource` 用于审计世界刷新、EncounterProfile、召唤 Ability、剧情脚本和技术演示来源，不参与敌我判断。
- `encounterId` 只声明预期上下文；spawn 与 `encounters.join()` 必须形成原子操作或完整回滚，禁止生成“半加入”Actor。

运行时 `ActorInstance`：

```js
{
  id,
  blueprintKey,
  actorRecordId,
  level,
  tier,
  partyId,
  teamId,
  factionId,
  controllerId,
  lifecycle,
  components: {
    transform,
    body,
    vitals,
    statBlock,
    modifierLedger,
    resources,
    actionState,
    cooldowns,
    comboState,
    statuses,
    targeting,
    movement,
    presentation
  }
}
```

- `transform`、`lifecycle` 和 `presentation` 是可渲染 Actor 的基础组件；其他组件按 Blueprint 能力存在。战斗系统不得假设所有 Actor 都有 vitals 或 actionState。
- ActorInstance 只保存 `blueprintKey` 的运行时引用；快照可输出该 key 用于诊断，但存档不得保存或依赖它。

公开入口：

```js
Game.roster.primaryActor();
Game.roster.activeParty();
Game.roster.createRecord(spec);
Game.roster.getRecord(actorRecordId);
Game.roster.removeRecord(actorRecordId, reason);

Game.actors.spawn(spec);
Game.actors.get(actorId);
Game.actors.query(filter);
Game.actors.despawn(actorId, reason);
Game.actors.snapshot(actorId);
Game.actors.inspect(actorIdOrBlueprintId);

Game.parties.create(spec);
Game.parties.addMember(partyId, actorId);
Game.parties.removeMember(partyId, actorId);
Game.parties.members(partyId);
```

- `createRecord()` 只创建长期记录，不自动生成世界实例；`removeRecord()` 必须拒绝删除主 Actor 或仍被 party/世界实例引用的记录。
- `Game.world.hero` 暂保留为主 Actor 查询兼容 getter，不再拥有独立实体模型。
- 新代码通过稳定 Actor ID、roster 或 actors API 访问主角。
- `snapshot()` 返回可序列化只读快照；`inspect()` 返回卡片、编译来源、派生属性和引用诊断。

### 6. 阵营、队伍、控制器与关系

长期阵营首批包含：

- `adventurers`
- `wild`
- `forest_guardians`
- `mine_denizens`
- `undead`
- `frost_clans`
- `infernal`
- `ruin_guardians`
- `demon_army`

关系接口：

```js
Game.relations.resolve(sourceId, targetId, encounterId);
Game.relations.setOverride(scope, sourceId, targetId, relation, options);
Game.relations.clearOverride(overrideId);
```

- 返回 `self | ally | neutral | hostile`。
- 优先级：Actor 临时覆盖 → encounter team 覆盖 → faction 矩阵 → `neutral`。
- 关系允许方向性解析；默认阵营敌对关系可对称，魅惑、保护和剧情规则不要求对称。
- `partyId` 表示长期协作容器，`teamId` 表示当前 encounter 立场，`factionId` 表示世界长期关系。
- `controllerId` 首批使用 `player`、`ai:player-auto`、`ai:monster`、`script`。
- 当前正式 `party-player` 只有主角；技术演示必须真实支持四名友方和八名测试敌人。

## Stats, damage, resources and statuses

### 1. StatDefinition 与 ModifierLedger

核心属性：

- 生存：`maxHp`、`armor`、`ward`
- 输出：`physicalPower`、`magicPower`、`accuracy`
- 时间轴：`gcdSpeed`、`castSpeed`、`autoAttackSpeed`、`cooldownRate`
- 移动：`moveSpeed`、`range`
- 随机：`critChance`、`critMultiplier`、`dodgeChance`
- 支援：`healingPower`、`shieldPower`、`lifesteal`
- 控制：`statusPotency`、`tenacity`、`interruptPower`
- 职责：`threatMultiplier`、`resourceRegen`
- 收益：`expMultiplier`、`goldMultiplier`、`dropMultiplier`

每个 StatDefinition 声明：

- 默认值、数值类型、合法范围和硬上限。
- 参与的 modifier phase 和同组聚合方式。
- 是否允许进入装备、状态、永久升级和临时 encounter 修正。
- Inspector 显示格式与 i18n key。

派生顺序固定为：

`基础值 → 等级/阶位成长 → 装备平值 → 其他平值 → 加算百分比 → 乘算修正 → 状态修正 → 上下限`

- `ActorInstance.components.statBlock` 是 dirty flag 缓存，不是任意系统可直接修改的可变属性字典。
- 所有增减益写入 `modifierLedger`，记录来源、stat、phase、operation、value、有效期和 stackingGroup。
- 旧 `atk/def/spd` 在迁移适配层映射到新属性，不进入新内容 schema。

### 2. DamageType 与伤害管线

首批伤害类型：

- 物理：`slashing`、`piercing`、`blunt`
- 魔法：`arcane`、`fire`、`frost`、`lightning`、`poison`、`radiant`、`necrotic`
- 特殊：`true`

结算顺序：

`合法目标 → 命中/闪避 → 基础公式 → 暴击 → armor/ward → 类别抗性 → 具体抗性 → 易伤/减伤 → 护盾 → HP → 吸血/反应 → 死亡检查`

- 物理读取 `armor`，魔法读取 `ward`，之后应用类别与具体类型抗性。
- `true` 跳过防御和抗性，但仍受明确声明的通用免伤或 encounter 规则约束。
- 所有随机判定从 Encounter RNG 获取，按稳定 Actor ID、Ability ID、Effect index 和 sequence 形成可重放顺序。
- 伤害上下文记录原始值、各阶段修正、吸收量、最终值和标签，供 Inspector 与测试审计。

### 3. ResourceDefinition

资源定义支持：

- `min/max/initial`
- encounter 开始、结束、死亡和脱战时的重置策略
- 固定、按 tick、按事件或按条件恢复
- 溢出、负值、消耗预留和退款规则
- UI 显示、颜色、刻度和可访问文本

HP 可按 ActorRecord 规则持久化；怒气、连击点、奥术层等 encounter 资源默认不持久化。

### 4. StatusCard 与状态实例

StatusCard 支持：

- `unique`、`refresh`、`stack`、`replaceStrongest`、`independent`
- 唯一键维度：全局、每来源、每 Ability、每标签组
- 最大层数、刷新方式、互斥组和替换优先级
- `snapshot | dynamic` 强度策略
- 持续时间、周期 tick、驱散类别、免疫标签、控制分类
- Modifier、DOT/HOT、护盾、沉默、减速、定身、眩晕、增减伤、光环和事件反应

状态实例记录：

```js
{
  id,
  statusId,
  sourceActorId,
  sourceAbilityId,
  appliedTick,
  expiresTick,
  nextPeriodicTick,
  stacks,
  potencySnapshot,
  shieldState
}
```

- 护盾必须声明吸收类型、优先级、来源和过期行为。
- 普通控制单次不超过 1.25 秒；Boss 依靠 tenacity 和递减规则缩短控制，不使用完全免疫封死职业。
- 同 tick 状态到期、周期触发和伤害结算使用固定 phase 顺序。

## 固定时间轴确定性自动战斗

### 1. CombatRulesProfile

正式默认 profile：

- `tickMs: 50`，战斗逻辑 20Hz。
- `baseGcdTicks: 40`，即默认 2.0 秒。
- `gcdFloorTicks: 24`，即 1.2 秒。
- `queueWindowTicks: 7`，即 350ms。
- `defaultGcdLockTicks: 12`，即 600ms。
- `defaultOgcdLockTicks: 9`，即 450ms。
- 两次 GCD 之间默认最多一次 oGCD；Reaction 可按能力契约绕过。
- 自动攻击默认 48 tick，即 2.4 秒，只是可选 Action，不承担职业主要轮转。

这些是 `core.rules.standard-v1` 的数据默认值，不是不可替换的引擎常量。职业、状态或特殊 encounter 只能通过受控 modifier 改变允许开放的字段。

- 所有会影响战斗结果的时间必须在内容编译时归一为整数 tick；运行时不得混用浮点秒计时器。
- 禁止保留旧式“每个实体独立攻击倒计时＋技能冷却到点立即触发”作为隐藏旁路；自动攻击、技能、Reaction 和机制都必须进入统一 Action/事件管线。
- 世界移动和 Canvas 动画可以按 render delta 平滑表现，但进入射程、离开预警、施法完成、命中和状态周期等战斗判定只在固定 tick 边界提交。
- 渲染积压时 combat 使用有上限的 fixed-step catch-up；不得通过丢弃逻辑 tick 改变结果。长时间后台或离线切换到既定暂停/摘要路径，不无限补算主线程 tick。

### 2. EncounterInstance

```js
{

  profileId,
  lifecycle,
  tick,
  seed,
  rngState,
  nextSequence,
  participants,
  teams,
  relationOverrides,

```

- 每个 Actor 同时至多参加一个正式 encounter。
- `threatTables` 按敌对观察者保存其对合法目标的威胁，不存回 Actor。
- scheduler 使用 `dueTick + phase + sequence` 稳定排序，不依赖对象遍历顺序。
- `eventLog` 正式游戏保留有限 ring buffer；技术演示和测试可启用完整日志。
- encounter 负责开始、加入、脱战、胜负、清理和奖励授权；经济系统响应结算事件后入账。

公开入口：

```js

Game.combat.modifyResource(context);
Game.combat.modifyThreat(context);
Game.combat.defeat(actorId, context);
```

### 3. 行动状态与结算阶段

行动状态：

`idle → queued → casting/channeling → resolving → recovering`

旁路状态：

`moving | interrupted | disabled | defeated`

单个 Action 固定管线：

`Command → Validate → Reserve → Start → Cast/Channel → Resolve → Reactions → Commit → Cleanup`

- `Validate` 检查关系、目标、距离、视线、资源、冷却、状态和 encounter 生命周期。
- `Reserve` 预留资源和 charge，取消时按 Ability 契约退款。
- `Resolve` 按 effect index 依次执行；结构化事件先入队，禁止任意递归直接调用。
- `Reactions` 设置单事件触发次数、单 tick 预算和最大递归深度。
- `Commit` 统一提交资源、冷却、威胁、死亡和统计。
- `Cleanup` 处理到期状态、目标失效、脱战和 encounter 完成。

相同编译内容、初始快照、命令、策略和 seed，在不同渲染帧划分、浏览器刷新率和无渲染模拟下必须得到相同事件摘要。

## Job kits, talents and combat AI

### 1. 五职业资源与基础轮转

- 战士：Tank；`rage 0–100`。三段基础斩击建立怒气与防御层，重击/旋风消耗怒气，战吼和防御技作为 oGCD；受到伤害生成少量怒气。
- 盗贼：Melee DPS；`energy 0–100`、`comboPoints 0–5`。能量自然回复，基础攻击构筑连击点，背刺/毒击消费，闪避和爆发为 oGCD。
- 法师：Magic Ranged DPS；`mana 0–10000`、`arcaneCharges 0–4`。法术建立奥术层并提高威力与消耗，爆发技能清空层数，屏障和法力恢复进入防御循环。
- 牧师：Healer/Support；`mana 0–10000`、`faith 0–100`。惩击建立信仰，治疗、护盾和光耀技能消费；单人时合法选择自己，未来队伍按职责选择友方。
- 游侠：Physical Ranged DPS；`focus 0–100`、单一 `markedTargetId`。基础射击积累专注，强力射击和多重射击消费，标记提高优先级并提供团队接口。

要求：

- 每个职业必须拥有不依赖技能点的合法基础轮转，连续运行 10 分钟不资源死锁、不永久空转。
- 现有 30 个技能的稳定 ID、等级、解锁和技能点投资保持兼容。
- 每个职业在单人正式玩法中都具备完整输出和生存闭环；Tank/Healer 是未来队伍职责，不得导致单人职业只能等待队友。
- 不使用无法解释的隐藏“单人伤害翻倍”；差异通过正式 Action、Trait、资源和 AI 表达。

### 2. TacticsProfile

内置策略：

- `safe`：5 tick / 250ms 机制反应延迟；预计伤害超过最大生命 5% 时考虑躲避，65% HP 以下提高防御优先级。
- `balanced`：8 tick / 400ms 延迟；预计伤害超过 12% 时考虑躲避，45% HP 以下提高防御优先级；默认。
- `aggressive`：13 tick / 650ms 延迟；预计伤害超过 22% 才放弃输出，30% HP 以下提高防御优先级。

允许玩家覆盖的战术字段：

- Ability 启用/禁用。
- 治疗和防御生命阈值。
- 必须打断的 cast tag 与优先级。
- 单体/AOE 切换条件。
- 资源保留比例和爆发窗口策略。
- 优先目标标签和手动 priority target。

三种内置策略是可编辑配置的预设，不建立三套 AI 代码。

### 3. 决策模型

统一优先级：

`避免致命机制 → 紧急治疗/防御 → 必须打断 → 维持职责 → 高价值资源消费 → 连段 → 填充 Action → 自动攻击`

- AI 感知默认每 2 tick 评估一次，但不得绕过 GCD、动画锁、施法、资源、距离、视线和 relation。
- AI 在 reaction delay 到期前不能使用尚未获得的预警安全点信息。
- 正在施法时评估取消损失；取消仍通过 combat API 执行。
- 多个预警重叠时按预计伤害、控制强度、到期 tick 和路径成本选择安全点。
- 所有平分结果按显式优先级、Actor ID、Ability ID 排序，不使用无 seed 随机。
- 玩家指定的 priority target 在合法且存活时优先；失效后恢复 TacticsProfile。
- 敌方默认选择自身威胁表中最高的合法目标；嘲讽可抬高威胁或生成有限时强制目标规则。
- Ability 只提供可复用 `aiHints`，完整决策权属于 AI/TacticsProfile，禁止在每个技能内编写专用函数。

### 1. EncounterProfile

区域不再只登记 monster ID，而是引用 EncounterProfile：

```js

  schemaVersion,
  regionId,
  rulesProfileId,
  packs: [{
    id,
    members,
    weight,
    spacing,

  }],

```

- 普通 pack 包含 1–3 个敌人，共享警戒、leash、team 和 encounter 生命周期。

- 只有当前 pack 加入 encounter，禁止整张地图连锁围攻。
- 多怪奖励按 encounter `rewardBudget` 归一，不因成员数量线性放大经济。

- 玩家撤离、死亡、超出 leash、回营或切区时统一结束 encounter，清除临时资源、威胁、状态和预警，并执行现有世界规则。
- 世界掉落仍由奖励结算后的物品事务生成；encounter 不直接操作背包或金币。

### 2. 怪物机制预算

普通怪：

- 一个基础 GCD 攻击
- 一个被动 Trait
- 一个签名 Action、施法或 Reaction

Boss：

- 共享 `boss_resolve`
- 一个独特被动 Trait
- 三个正式 Action
- 一个 50% HP phase rule
- 可选一次性增援；战场敌方上限仍为 3

主题机制：

| 区域 | 普通怪 | Boss |
|---|---|---|
| 草原 | 史莱姆腐蚀护甲；灰狼施加流血并追击低生命目标 | 史莱姆王：圆形重压、扇形黏液波、可打断再生；半血分裂两只小史莱姆 |
| 森林 | 毒菇读条释放毒雾；树苗使用根须减速 | 远古树人：根须圆阵、枝干扇扫、可打断复苏；半血提高施法频率 |
| 矿坑 | 蝙蝠尖啸降低命中；矿工碎甲 | 石魔像：震地圆环、岩盾、重型单体攻击；半血核心开裂提升伤害并降低防御 |
| 墓地 | 骷髅盾击；鬼火吸取生命 | 死灵法师：暗影箭、凋零诅咒、骸骨屏障；半血召唤两名骷髅 |
| 雪山 | 冰狼叠加寒冷；雪怪蓄力重击 | 霜巨人：直线冰矛、延迟雪崩、冰川护甲；半血白化风暴限制安全区 |
| 熔岩 | 火焰小鬼灼烧；熔岩蜥蜴反伤与撕咬 | 火焰恶魔：狱火斩、火焰护盾、连续喷发；半血过热加速 GCD |
| 遗迹 | 守护球压制光束；女妖俯冲和音爆 | 遗迹守卫：奥术射线、重力场、护盾重校准；半血超频并缩短读条 |
| 魔王城 | 魔族士兵诅咒横斩；石像鬼石化减速 | 魔王：深渊之刃、黑暗敕令、魔王壁垒；半血进入暴君阶段并召唤两个短时暗影目标 |

- 普通怪不得拥有硬免疫。
- Boss 抗性和 tenacity 提供部分抵抗，不让任何职业失去主要输出或资源闭环。
- 自动 AI 必须能够处理全部正式机制；不得依赖玩家手动技能操作才能避免永久失败。

## Content authoring and fast addition contract

### 1. 新增单位的标准路径

实现期必须交付 `docs/content-authoring/adding-actor.md`，内容与本节保持一致，并提供至少一个最小单位和一个完整机制单位示例。标准步骤：

1. 选择已有 Pack 或创建具备稳定 ID、版本、schemaVersion 和依赖声明的新 Pack。
2. 创建 ActorArchetypeCard，只填写身份、表现、身体、默认阵营和实际需要的 profile/trait 引用。
3. 在同一纵向 Pack 或明确依赖的 Pack 中添加 Stat、Resource、Ability、Trait、Status、AI、Reward 等引用定义。
4. 补齐 `zh-CN`、`en` 文本 key、sprite/portrait/render profile 和无障碍文本。
5. 将战斗单位挂入 EncounterProfile；将 NPC 挂入明确的世界生成/交互配置；不得在 world 或 UI 写单位 ID 特判。
6. 运行内容严格审计、引用图、i18n/资产检查、确定性战斗测试和 Actor / Combat Lab 深链检查。
7. 只有实际发布修改 HTML/CSS/JS/字体时，才统一提升 BUILD_ID 并执行缓存版本测试。

文档必须明确：

- 稳定 ID 命名、Pack 所有权、版本与 patch/replace 规则。
- Card、Record、Blueprint、Instance 和 Encounter 的生命周期区别。
- 哪些字段可省略、默认值来自哪里、错误如何定位到 sourcePack/sourceFile/field path。
- 普通怪、Boss、NPC、持久同伴和召唤物的最小模板与完成定义。
- 如何在 Lab 通过 `unit`、`encounter`、`strategy`、`seed`、`scenario` 深链复现。
- 禁止事项：内联函数、无 seed 随机、category 敌我判断、直接改存档、复制生产规则、为单一单位增加引擎分支。

### 2. 各类单位的最小完成定义

普通怪：

- ActorArchetype、Stat/Resistance、基础 GCD、一个 Trait、一个签名机制、AI、Reward、Faction。
- 至少被一个区域 EncounterProfile pack 引用。
- 通过单怪和 1–3 怪共享 encounter 测试。

Boss：

- 满足普通怪全部要求，并增加三 Action、共享 `boss_resolve`、50% HP phase、预警/打断契约和可选增援预算。
- 有独立 boss encounter、巢穴映射和阶段确定性测试。

NPC：

- ActorArchetype、Presentation、Body、Faction、Controller 和明确世界生成来源。
- 非战斗 NPC 不必伪造 HP、攻击或空 AI；如可转为战斗状态，必须通过正式组件/Blueprint 变体和 relation 变化完成。
- 交互行为由未来 InteractionProfile 或现有世界交互适配器承载，不写入 renderer，也不由 `category === 'npc'` 自动推断。

持久玩家/同伴：

- ActorArchetype 加 Class/Loadout/Talent 等组合层，并由 `Game.roster.createRecord()` 创建长期记录。
- 存档只保存稳定 archetypeId、classId 和成长数据；运行时 Blueprint 与 Instance 可随内容 fingerprint 重建。

召唤物：

- 独立 ActorArchetype，由 `summon` Effect 生成；显式声明寿命、数量上限、controller/faction/team 继承和离场规则。
- encounter 内实例 ID、加入顺序和 RNG 必须由 encounter sequence 确定；不得持久化为 ActorRecord。

### 3. 作者工具与自动验收

- 可以提供 `tools/scaffold-actor.ps1` 或等价脚手架生成 Pack/Card/i18n/测试模板，但脚手架不是第二套 schema，也不能自动修改引擎行为。
- 提供 Node 可运行的内容审计入口，使新增内容不必启动完整 UI 即可得到结构、引用、i18n、资产、重复 ID、循环和 fingerprint 结果。
- 增加 authoring smoke fixture：只新增测试 Pack 和内容映射即可生成一个普通怪、一个中立非战斗 NPC 和一个召唤物，正式引擎文件零修改。
- 正式游戏与全部相关技术演示的内容清单必须做集合相等测试，避免新增单位只在某个入口可见。

## Persistence, compatibility and dependent systems

### 1. 存档 v12

```js
{
  v: 12,
  roster: {
    primaryActorId: 'player-main',
    activeParty: ['player-main'],
    actors: {
      'player-main': {
        archetypeId: 'adventurer',
        classId,
        level,
        exp,
        skillPoints,
        talentRanks,
        permanentUpgrades,
        persistentResources: {
          hp
        },
        loadout: {
          equipment,
          lockedSlots
        }
      }
    }
  },
  economy: {
    gold,
    crystal
  },
  inv: {
    items,
    potions,
    materials
  },
  settings: {
    combatStrategy: 'balanced',
    combatTactics: {}
  }
}
```

持久化边界：

- 保存长期 ActorRecord、party 配置、世界进度、经济、背包和玩家战术配置。
- 不保存 encounter、GCD、施法、威胁、预警、临时状态、怒气、连击点、奥术层和临时召唤。
- 读档总是从合法脱战状态恢复；持久 HP 按现有休息、死亡和离线规则处理。
- `ActorInstance`、CompiledActorBlueprint、blueprintKey 和内容定义不得直接序列化进存档。

迁移：

- v11→v12 将旧 `player`、`inv.equipped`、锁槽、技能、永久强化和 HP 无损迁入主 ActorRecord，并写入稳定 `archetypeId: 'adventurer'`。
- 旧 `player.gold/crystal` 迁入 economy；物品、药水和素材结构保持稳定。
- 更老存档继续依次迁到 v11，再进入 v12。
- 职业 ID、现有技能 ID、物品 UID、区域 ID、世界种子、探索记录和资产 ID 保持不变。
- 缺失职业时退回职业选择并返还已投入 Talent 点。
- 缺失 Talent 时按保存 rank 返还技能点；缺失主 Actor archetype 时回退 `adventurer`。
- 缺失装备定义继续沿用现有折算规则；损坏的 encounter 临时字段直接丢弃。
- `Game.player` 暂作为主 Actor和 economy 的兼容门面，按模块迁移 UI、自动养成、物品、离线、结局和商店后缩减为只读/命令适配器。

### 2. 兼容切换原则

- 重构期间允许旧引擎继续服务正式游戏，同时 V2 在技术演示和测试中运行。
- 不允许两个引擎同时修改同一正式存档、经济或世界实体。
- 旧引擎只用于生成不可变基线和保障生产版本；正式切换完成后删除旧战斗路径，不长期双轨维护。
- 新事件通过适配器兼容旧事件消费者；旧系统不得反向成为 V2 结算依据。
- 任何兼容 getter、字段映射或事件别名都要登记移除条件和覆盖测试。

### 3. CombatEstimator 与离线收益

```js
Game.combatEstimator.evaluate({
  partySnapshot,
  encounterProfileId,
  tacticsProfile,
  sampleSeeds,
  maxTicks
});
```

- 使用与在线战斗相同的 Blueprint、Ability、Status、Resource、AI、CombatRules 和 encounter 规则进行无渲染加速模拟。
- 缓存键包含内容 fingerprint、party 构筑、装备、Talent、等级、区域、encounter、策略和 sample seed 集。
- 等级、装备、Talent、职业、区域或战术变化时使相关缓存失效；评估采用防抖和分块执行，不阻塞主循环。
- 当前区域分别模拟代表性单怪、双怪、三怪和 Boss 前置场景，生成平均战斗时长、失败率、资源稳定性和奖励摘要。
- 离线长时间结算使用缓存摘要，不逐 tick 模拟整段离线时间。
- 离线不得揭雾、首次发现、触发 Boss、阶段剧情、区域解锁或生成实时 encounter。
- 自动换装、自动 Talent 升级和战力展示统一读取 Estimator，不再解析旧技能字段或维护职业特判公式。

## World, rendering, UI and technical demo

### 1. 世界与移动

- 世界工厂统一改为 `Game.actors.spawn()`；刷怪只提供 blueprint、tier、team、faction、controller、位置和 encounter pack 上下文。
- 开放探索的 threat territory 改为 encounter pack anchor；现有生成坐标、迷雾、导航、资源和地标协议不因战斗重构改变。
- `Game.combatAI` 返回行动/移动意图；寻路、避开预警、进入射程、leash 和世界碰撞由 world/nav 执行。
- 索敌、AOE、击杀、可攻击性和 AI 判断读取 relation、team、component 和 encounter，不判断 `kind === 'hero'/'monster'`。
- 角色专属回营、探索揭雾和交互权限通过 controller、roster role 或显式 component 判断，不通过 sprite/category 推断。
- 传送、休息、死亡、切区和结局进入前必须安全结束当前 encounter。

### 2. 正式 UI

增加：

- 当前 GCD、行动进度、职业资源和 combo 状态
- 主角状态图标和有限 party list
- 敌方施法条、可打断标记、地面预警和 Boss phase
- priority target 标记
- 安全/均衡/激进策略和有限 Tactics 配置
- 单成员队伍框架；DOM 结构支持未来四名成员
- 中英文可访问文本、非颜色唯一提示和减少动态效果适配

不增加：

- 手动技能热栏
- 正式多同伴玩法
- 完整开发者 Inspector 或全量战斗日志

### 3. Actor / Combat Lab

`tech-demos/units` 升级为 Actor / Deterministic Combat Lab：

- 自动枚举全部 ActorArchetype，并按 player、monster、npc、companion、summon、object 分类；首期至少覆盖 5 职业、16 个普通怪、8 个 Boss，以及 Ability、Talent、Status、Resource、AI、Faction 和 EncounterProfile。
- Inspector 展示原始 Card、编译 Blueprint、引用来源、派生属性、ModifierLedger、资源、轮转、状态、抗性、关系和审计结果。
- 可生成 1–4 人队伍与 1–8 个测试敌人。
- 可生成中立/友方/敌对 NPC、无战斗组件 Actor、召唤物和可战斗 object，验证它们仍复用同一 `actors.spawn()` 与关系系统。
- 可调整 faction、team、controller、strategy、level、tier 和 relation override。
- 支持暂停、单 tick、倍速、指定 Action、施加/驱散 Status、打断和移动 Actor。
- 实时显示 tick、scheduler、资源、cooldown、combo、状态层数、威胁表、当前 Action 和结构化 CombatEvent。
- 内置 GCD/oGCD、资源耗尽/恢复、combo、打断、施法取消、重叠预警、治疗威胁、嘲讽、友方治疗、中立不可攻击、AOE 友伤过滤、魅惑、召唤和 Boss phase 场景。
- 保留 `region`、`unit` 深链，新增 `encounter`、`strategy`、`seed`、`scenario` 参数。
- 页面必须直接使用生产 content/actors/encounters/combat/render 模块，不复制模拟实现。

- 调整五职业、1–3 怪 pack、Boss 和离线摘要，使宏观基线满足目标。
- 更新主规划、README 和 `tech-demos` 文档，删除“伪实时、1v1、技能按冷却自动释放”的现行描述；新增单位文档与最终 schema、目录和工具保持一致。

Gate：

- 不存在生产双战斗引擎。
- 完整测试、性能、浏览器、移动端、i18n 和缓存验收通过。
- 发布前统一提升 `BUILD_ID`，不得在中间阶段重复消耗发布 ID。

## Test plan and acceptance

### 1. 内容与编译

- Pack 依赖、schema、重复 ID、显式 patch/replace、引用图、循环、i18n、资产、公式、handler 和 fingerprint。
- 5 职业、30 Talent、16 个普通怪、8 个 Boss、8 区域及全部 Ability/Status/Resource/EncounterProfile 零失联引用、零未映射定义。
- 编译结果深冻结；正式运行期间不能新增、覆盖或修改核心定义。
- 正式游戏、技术演示和 Node 审计加载的 Pack ID、版本和 fingerprint 一致。
- 作者 smoke fixture 只增加内容 Pack 即可注册、生成并检查普通怪、中立非战斗 NPC 和召唤物，生产引擎文件零修改。
- `adding-actor.md` 的最小示例可直接通过当前 schema 和严格审计，示例字段不会随实现漂移。

### 2. 时间轴与确定性

- 固定 tick、render dt 分割一致性、scheduler 稳定排序和 seeded RNG。
- GCD、oGCD、queue window、动画锁、施法、引导、charge、shared cooldown、取消、退款、打断和恢复。
- 不存在旧独立攻击倒计时或“冷却结束即旁路施放”；自动攻击、AI 技能和 Reaction 全部产生统一 Action/CombatEvent。
- 世界移动与动画使用不同 render dt 时，进入射程、离开预警、施法完成和命中提交 tick 一致；catch-up 上限不会静默丢逻辑 tick。
- 相同 seed/输入重复运行事件摘要一致；不同 seed 只在允许的随机节点产生差异。
- Reaction 最大深度、单 tick 预算、repeat 和 triggerAbility 防无限循环。

### 3. 属性、伤害与状态

- modifier phase、stackingGroup、dirty cache、上下限和来源移除。
- 物理/魔法/真实伤害、命中、暴击、闪避、armor、ward、抗性、易伤、护盾、吸血和死亡。
- DOT/HOT、snapshot/dynamic、叠层、刷新、互斥、驱散、免疫、tenacity、光环和同 tick phase 顺序。

### 4. Actor、关系、队伍与威胁

- self/ally/neutral/hostile、方向性关系、Actor override、team override、faction fallback。
- party 与 team 分离、controller 切换、召唤继承、魅惑易主和友伤过滤。
- 伤害、治疗、护盾、倍率、嘲讽、目标死亡、离开 encounter 和脱战清理。
- Record 创建、Blueprint 重建、SpawnSpec 校验、spawn/join 原子性、despawn 不删除 Record、确定性 instanceId 和 ID 冲突拒绝。
- 无 combat 组件 NPC、可战斗 object 和 world prop 的边界测试；category/rank/sprite/sourceFile 改变不影响 relation 或可攻击性。

### 5. AI、轮转与 Encounter

- 五职业 10 分钟资源与轮转测试。
- 三种策略的 reaction delay、预警走位、施法取消、priority target、治疗、防御和确定性平分。
- 1–3 怪共享警戒、leash、威胁、AOE、奖励预算、撤离、死亡和切区。
- 8 Boss 的正式 Action、半血 phase、打断、预警、增援上限和状态抵抗。
- 所有正式机制都能由自动 AI 完整处理，不依赖隐藏玩家操作。

### 6. 存档、离线与依赖系统

- v1–v11 全链迁移至 v12，Base64/JSON、主备份槽、职业、Talent、装备、HP、货币、路线、世界种子、探索和结局记录保持一致。
- 缺失职业、Talent、archetype、装备和损坏临时字段的降级路径。
- Estimator 缓存失效键、seed sample、在线/无渲染规则一致性。
- 离线收益、自动换装、自动 Talent 升级、商店、物品、成就、统计、音频和结局兼容事件。

### 7. 平衡

- 先生成不可变 V1 宏观基线，再运行 `5 职业 × 8 区域 × 100 世界种子`。
- 比较每职业首通时间中位数、区域死亡率、收益率、离线摘要和最终通关率。
- 最终目标处于旧基线 ±10%，无职业被任一区域机制、资源循环或抗性硬锁。
- 多怪 encounter 不要求旧单场 TTK 等价，但不得破坏既有整体探索推进包络。

### 8. 性能、浏览器与现有回归

- Lab `4 友方＋8 敌方` 下单次 50ms combat step P95 不超过 2ms；正式 `1＋3` 场景保持约 60 FPS。
- 定义只编译一次；statBlock 使用 dirty flag；目标查询复用空间索引；事件日志使用有界 ring buffer。
- Actor / Combat Lab 覆盖桌面、390×700、390×844、522×1320、中英文、暂停、单步、倍速、深链和无横向溢出。
- 保留并运行现有 v1–v11 存档、开放探索 v3、布局、平衡、动作气泡、交易、最终区域锁、浏览器 smoke 和缓存测试。
- HTML/CSS/JS/字体发布前统一运行 `tools/set-build-id.ps1`，执行 `node tests/cache-version.test.js` 和完整回归；禁止只更新单个资源查询版本。
- 性能门槛必须记录浏览器、硬件、预热次数、采样窗口和统计方法；CI 使用稳定 smoke 阈值，完整 P95 与平衡矩阵作为发布验收，避免环境噪声造成伪失败。

## Assumptions and non-goals

- 首期不开放正式同伴、职业切换、子职、多职业、玩家多队伍、关系好感或对话检定。
- Party、治疗友方、团队增益、威胁、召唤、易主和四人 AI 必须在 Lab 中真实运行，不只保留空字段。
- 正式战斗完全自动，但玩家仍可探索、指定 priority target、配置 Tactics、切换策略和撤离。
- 保留纯前端、离线、`file://`、普通 `<script>` 和 `Game.*` 全局命名空间，不引入构建期框架或运行时依赖。
- 不以面向对象继承层级衡量扩展性；Player、Monster、NPC 的差异通过可组合内容、关系、控制器和可选组件表达。
- 内容复杂度通过可组合定义、编译契约、调试工具和测试覆盖获得，不通过无消费者的预留字段或抽象层数量获得。
- 实施时保留当前工作区已有的 Units 自动枚举、动作气泡和开放探索修改，在其上增量重构，不覆盖无关改动。
