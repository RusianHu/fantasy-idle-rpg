## 评估结论

- 当前 24 只怪物、16 个 Encounter 彼此一致，内容审计及 V2 运行测试全部通过，现有内容没有损坏。
- "新怪物注册入口"并不准确。怪物需要同时存在于旧 [monsters.js](C:/Users/admin/Desktop/HBC%20Web/fantasy-idle-rpg/js/data/monsters.js:10)、新 Pack，以及区域/地图列表；[world.js](C:/Users/admin/Desktop/HBC%20Web/fantasy-idle-rpg/js/systems/world.js:338) 又同时读取两套定义。实测仅注册合法 Actor Pack 可以通过严格审计，但无法进入世界。
- [factory.js](C:/Users/admin/Desktop/HBC%20Web/fantasy-idle-rpg/js/data/packs/regions/factory.js:101) 固定假设"2 普通怪 + 1 Boss"，不支持任意数量、跨区复用、和平变体或 NPC 遭遇。
- patch 机制对数组是整体替换（`compiler.merge`），多个 Pack 修改同一区域生态会互相覆盖，无法支撑"加一只怪只写一个文件"的批量工作流；这是采用反向挂载语义的直接动因。
- 当前 Relation 只能表达 `ally/neutral/hostile`。中立单位不能被世界点击、Action 选中或伤害；不同 Encounter team 又会被强制视为敌对，无法容纳旁观者、护送者或临时中立第三方。
- `variantId` 目前只参与缓存键，不改变 Blueprint；NPC 也不会被正式世界更新、渲染或结算。世界级 relation override 缺少生命周期清理，Actor ID 重置后还有串状态风险。
- 离线结算存在双通道：世界内击杀收益走 rewardProfile，[offline.js](C:/Users/admin/Desktop/HBC%20Web/fantasy-idle-rpg/js/systems/offline.js:28) 仍直接读 `region.monsters + formulas.monsterStats`。两通道常数同源（hp 55/2.05/Boss×11，exp 12/1.95/×18，gold 7/1.9/×14），合并通道时必须以等价断言锁定。
- 结论：内容本身健康，但作者入口、跨注册审计和高级生态能力不合格。允许只发布一次，但实现内部必须按“内容产物 → Population/Region 等价迁移 → 通用世界 Spawn → Engagement/Objective/Variant → 存档与 UI”设置可独立验证的兼容检查点，禁止直到最后才整体联调。

## 目标架构与接口

- 内容定义只保留一份，正式引用图固定为：`ActorArchetype → ActorVariant`；`EncounterPack → Actor/Variant members`；`WorldSpawnProfile → Actor/Variant | EncounterPack`；`WorldSpawnProfile —mountTo→ WorldPopulationProfile → RegionProfile`。这是“定义一次、反向挂载”：普通怪/战斗 NPC 的单位内容胶囊写自己的 archetype、可选 Variant、EncounterPack、WorldSpawnProfile 与 `mountTo`；单体 NPC/和平生物可由 WorldSpawnProfile 直接引用 Actor/Variant，不修改任何区域文件。
- 挂载聚合契约：`worldSpawnProfile.mountTo[]` 每条声明 `populationId`、`channel: regular | rare | guardian | npc | boss`、`mode: required | weighted` 与可选条件；`required` 声明正整数或 `[min,max]` 的 `count`、禁止有意义的 weight 并优先占用槽位，`weighted` 声明正整数 `weight` 与可选正整数 `maxCount`，按稳定 RNG 有放回填充剩余槽位但不超过 maxCount。条件白名单仅 tier 区间与 Population/Region 显式声明的布尔 flag，禁止读取任意状态路径或内联函数。Population 本体只声明各 channel 的容量、选择与槽位规则；编译后的最终 spawnRefs = 本体条目 + 聚合挂载，顺序固定为 Pack 拓扑序 → WorldSpawnProfile ID 字典序，与源文件/脚本加载顺序无关并计入 Population 局部 fingerprint。required 最小数量超过容量、无法满足 required、挂载目标缺失、同一 WorldSpawnProfile 对同一 Population/channel 重复挂载、非法 channel/mode/count/条件/权重均拒绝；审计必须输出每区各 channel 聚合视图与 Actor 到区域/Spawn/Encounter 的完整反向引用链。
- 新增 `actorVariant`：允许在不更换 ActorInstance ID 的情况下切换 stat/resource/ability/trait/AI/presentation/interaction/engagement profile；`compileBlueprint()` 真正解析 `variantId`，Blueprint 与 Actor 快照显式记录该 ID。Variant 只覆盖白名单字段，必须声明所属 `archetypeId`，继承和转换图禁止循环。
- 新增独立 `encounterPack`：声明任意数量成员、Variant、队形、leash、奖励预算与群体警戒；每个 member 必须有 Pack 内稳定 `slotId`，相同 Archetype 重复出现也不得依赖数组下标区分。EncounterPack 是可被世界、脚本、召唤和 Lab 复用的成员组，本身不声明世界挂载、刷新或坐标。
- 新增 `worldSpawnProfile`：以互斥的 `actorRef { archetypeId, variantId? }` 或 `encounterPackId` 声明出生内容，另声明反向 `mountTo`、身份范围、放置约束、激活/卸载/死亡/逃跑/重生策略与离线资格；它是“内容定义”进入“世界 Population”的唯一入口。EncounterPack 不再持有 `mountTo`。
- 新增 `worldPopulationProfile`：声明区域常规生态、稀有单位、守门精英、NPC、Boss 巢穴、各 channel 槽位、出现条件与离线代表单位，并接收 WorldSpawnProfile 聚合挂载。职责边界固定为：Population 管 What/How many（谁出现、权重、条件、容量），WorldSpawnProfile 管 How（身份与生命周期），layout 管 Where（合法坐标、巢穴与 guardian 位置仍由地形流生成）。
- 新增 `regionProfile`（全量迁移）：现有区域注册表的地形约束、探索、交易、采集与视差/粒子配置连同 Population 引用全部纳入编译内容；区域 Pack 使用与 factory 同型的确定性展开函数，展开输入与现 regions.js 完全一致。迁移后 `Game.reg` 的 region 注册表改为由编译内容自动填充的只读投影（旧消费方 API 不变），手写 `monster` Registry 与 `region.monsters/boss` 双写彻底删除；守门精英 4.2/1.55/1.45 等世界侧硬编码乘数移入精英/Population 定义。
- 新增 `engagementPolicy`，分别定义 `manualAttack`、`autoAggro`、挑衅触发、群体传播、脱战、逃跑、投降、奖励许可、记忆范围与声望后果。
- 新增 `interactionProfile`，使交谈、交易、攻击、任务等动作由能力与配置决定，不再由 `category === 'npc'` 推断。
- Relation 优先级调整为：Actor/Encounter 临时覆盖 → Encounter 显式 team 矩阵 → 世界 Actor/群体记忆 → 声望修正 → Faction 基线 → neutral。不同 team 不再自动敌对，team 也不再直接决定 Encounter 胜负。
- 增加 `Game.engagement.canInitiate()`、`requestAttack()`、`provoke()`、`forgive()`、`snapshot()`；`requestAttack()` 只提交不可变 `EngagementCommand`，不得在 DOM 事件或渲染帧内直接修改 Relation、Actor 或 Encounter。
- 增加 `Game.actors.transitionVariant(actorId, nextVariantId, options)`；默认只允许脱战转换，战中转换必须由已审计的转换边和 cleanup phase 驱动。转换先构建候选 Blueprint/组件快照，通过全部校验后一次提交，失败时 Actor、Encounter 和事件日志均保持不变。
- 普通点击优先交互；中立可攻击单位通过明确的剑图标动作和确认进入战斗。自动模式永不主动攻击中立单位，敌对状态建立后才允许自动接战和 AOE 命中。
- 分层敌对记忆采用数据默认值：实例记忆持续当前 Encounter，普通群体记忆持续 180 世界秒并入档，关键 NPC 记忆持续到赎罪事件，Faction reputation 持久化并可衰减或修复。
- 奖励语义：保持逐击杀即时发放与地面掉落协议不变。Encounter 编译时生成"奖励授权集合"，仅决定资格——observer、objective 与未授权 NPC 击杀不产生 exp/gold/掉落，NPC 不因具有 Vitals 自动掉落；leash、主动撤离、死亡等提前结束天然保留已发放收益。结束结果附带授权统计，只用于审计与测试，不参与发放。
- 数值同源：迁移以 formulas 常数为唯一数值源，区域展开函数继续消费 monsterStats 同源常数；`offline.settle` 与 CombatEstimator 改读编译 Population（`evaluateCurrent` 的首 pack 语义由 Population 首个常规条目继承，离线代表单位由 Population 显式声明）。legacy `ent.atk/def/spd` 世界字段随旧通道删除，审计确认无残余消费方。
- 存档升级至 v14，ActorRecord 增加可选稳定 `variantId`，并新增按稳定 `spawnId/socialGroupId/factionId` 索引的 `world.social`（含需持久化的 `spawnVariants`）；v13 迁移使用 Archetype/Population 默认 Variant 和空社交状态，不持久化临时 Actor ID、Blueprint key、Encounter 或战斗冷却。

### 内容源发现与 bundle 合同

- `js/data/packs/**/*.pack.js` 是正式 Pack 文件集合的唯一真源；`*.support.js` 只提供纯作者展开函数/已注册 handler，禁止注册 Pack；`js/data/content/manifest.generated.js` 与 `js/data/content/content.generated.js` 均为确定性生成物，禁止手改并位于 Pack 扫描根之外。迁移时将现有 15 个 Pack 源统一改名，`regions/factory.js` 及从 `core.js` 抽出的公式/handler 登记改为 support。
- `tools/build-content-bundle.js` 递归扫描规范化相对路径：support 文件各自必须且只能注册一个带稳定 ID/版本/依赖的 `ContentSupport` 描述，工具拓扑排序后在白名单 authoring/handler registry 中 install，再逐个执行 Pack。每个 `*.pack.js` 必须恰好调用一次 `registerPack()`，不得改写 Pack 注册表之外的全局状态；support 禁止注册 Pack，Pack 禁止注册 support。受限 VM 冻结其他 Game 表面，文件名、Support/Pack ID、`sourceFile`、重复 ID、依赖版本与循环全部校验，任何未归类的 `js/data/packs/**/*.js` 直接失败。
- Pack 允许在顶层声明随 Pack 一起发现和编译的 `locales: {'zh-CN': {...}, en: {...}}`；编译器先构建只读 locale 投影再做 i18n 审计。Pack 只能提供其 definitions 实际引用的内容 key；重复 key 只有两种文本逐字相同才允许，缺任一首发语言、隐式覆盖主语言包或携带未被本 Pack 引用的外部 key 均拒绝。locales、反向挂载视图与 objective/handler 版本都进入正式内容 fingerprint。这样新单位无需再新增语言脚本标签；无正式资产时脚手架只能引用已登记的通用确定性占位资产，不能靠关闭 missing-asset 审计放行。
- `js/data/content/content.generated.js` 不是简单 JSON 序列化，而是按上述受控顺序封装 support 与 Pack 源，保留现有确定性 factory 展开能力并兼容 `file://`；路径统一为区分大小写的 POSIX 相对路径，文本按 UTF-8 无 BOM、换行归一为 LF 后计算逐文件 SHA-256 与整体 `sourceSetHash`，生成物也固定 LF，保证 Windows/Linux 构建一致。文件头内嵌规范化源列表、哈希、Support/Pack 元数据和编译内容 fingerprint；注释等不改变 Card 的源修改仍会改变 sourceSetHash，不能只靠内容 fingerprint 判断陈旧。
- `js/data/content/manifest.generated.js` 记录相同的源列表与 `sourceSetHash`，供工具/诊断使用；正式入口、Actor / Combat Lab 和地图演示只加载 `js/data/content/content.generated.js`，运行时不加载源 Pack、support 或 manifest。Node 审计必须独立扫描并执行源文件，随后另起干净 VM 只加载 bundle，比较源文件集合、Pack 元数据、编译定义、反向挂载视图、内容 fingerprint 与 sourceSetHash，禁止两个路径共享同一个手写清单。
- `build-content-bundle.js --check` 只在内存重建预期 manifest/bundle 并逐字节比较磁盘产物，不写文件；新增、删除、改名、漏打包、重复打包和过期 bundle 均失败。`tests/cache-version.test.js` 同时断言所有 HTML 只引用当前 BUILD_ID 的 bundle；发布前顺序固定为完成全部源文件修改并重建 bundle → `--check` 与完整功能回归 → `set-build-id.ps1` 统一提升一次 BUILD_ID → `cache-version.test.js`，提升 BUILD_ID 后不得再改 HTML/CSS/JS/字体或 bundle；确需修改则重新执行该发布序列并使用新的 BUILD_ID。
- 单位脚手架创建“内容胶囊”：生成一个 `*.pack.js`（Actor/Variant/Ability/Interaction/Engagement/EncounterPack/WorldSpawnProfile 及 Pack-local 中英文 locales），并引用已登记的正式资产或通用确定性占位资产，然后自动重建并 `--check`。若作者随后补充独立正式素材，只需修改资产 manifest，不改区域/引擎。验收口径是“新增一个单位胶囊且不修改区域/引擎文件”；现阶段默认骨架可以真正只新增一个 Pack 文件。

### 稳定世界 Spawn、放置与生命周期

- `worldSpawnProfile.identity.scope` 取 `ephemeral | regionStable | worldStable`。所有已实例化世界单位都有本次会话可用的稳定键；`ephemeral` 不进入存档，`regionStable` 由区域/Population/Profile/布局槽位派生并允许 TTL 社交记录，`worldStable` 必须声明全内容唯一 `persistentKey`，用于跨区域移动的关键 NPC。编译器拒绝重复 persistentKey 或把可持久 Variant 挂在 ephemeral Spawn。
- 身份固定拆分为：`spawnId` 表示一个逻辑出生槽；`groupId` 默认等于 `spawnId + ':group'`，表示该槽共同出生的一组 Actor；EncounterPack member 再用稳定 `slotId` 区分；跨槽群体记忆另用显式 `socialGroupId`，禁止复用含义不清的 groupId；`spawnGeneration:uint32` 每次 materialize/重生递增；`ActorInstance.id` 仍只服务当前运行时。`regionStable spawnId = regionId + populationId + worldSpawnProfileId + layoutSlotKey`，`worldStable spawnId = world:<persistentKey>`；`ephemeral spawnId = session:<worldSpawnProfileId>:<spawnRequestKey>`，其中 Population 挂载使用 region/population/layoutSlotKey 组成 request key，召唤或脚本出生必须由确定性的 origin key 与 emission ordinal 提供 request key，缺失或同会话冲突即拒绝。数组遍历顺序、坐标小数、时间戳、随机 UUID 和 ActorInstance ID 禁止进入这些键。
- 世界维护 `SpawnLease {spawnId, groupId, generation, profileId, layoutSlotKey, actorIds, state}`；同一 spawnId 最多一个 active/materializing lease。重生复用相同逻辑槽并增加 generation；切区/读档清空 Lease 与 generation 计数属合法，因为命令队列也同时清空。`world.social` 只保存允许持久化的 spawnId/socialGroupId/factionId、绝对 `expiresAtWorldTime` 和 Variant，不保存 generation、Lease、坐标或实例 ID。
- `placement` 使用数据化 selector：`anchor(camp|bossPoint)`、`layoutEntity(guardian|threat|landmark|ecology + 稳定 id/tag)`、`candidate(spawnCandidates|corridorCandidates|walkableNav)`；支持确定性 offset、最小净宽/危险度/与营地距离、占位半径、`required` 和 `onFailure: rejectRegionMount | skipOptional`。解析只消费已生成 layout，不得改写地形 RNG、布局数组或黄金摘要；同一 seed/layout/content fingerprint 必须得到相同槽位与坐标。
- 槽位冲突按固定 channel 优先级 `boss → guardian → npc → rare → regular`，再按 required、显式 priority、WorldSpawnProfile ID、slot ordinal 排序；选择随机数只由 worldSeed、regionId、layoutVersion、Population ID、Profile ID、slot ordinal 和需要时 expeditionIndex 派生。新增非布局内容不得扰动已有地形流；是否允许扰动同一 Population 的加权 Spawn 选择由 Population fingerprint 明确界定。
- v3 直接复用已有 `region:threat:n`、`region:guardian`、landmark/ecology ID 作为 layoutSlotKey；v1/v2 不修改生成器或输出对象，挂载器在生成后以冻结的现有 `camp/bossPoint/spawnCandidates/corridorCandidates` 顺序合成 `camp`、`boss`、`candidate:n`、`corridor:n` 键。由此保持 v1/v2/v3 黄金布局逐字节不变，同时为三代布局提供稳定出生身份。
- 生命周期至少声明 `activation`、`unload`、`onDefeat`、`onEscape` 与 `respawn {mode:none|delay|worldTime, delay, resetVariant}`。区域卸载、死亡、逃跑与脚本 despawn 都先关闭 Lease、取消引用该 spawnId+generation 的未提交命令，再按 scope 清理 Relation/记忆；重生策略决定是否回到默认 Variant。离线只消费 Population 显式 `offlineEligible/offlineRepresentative`，不在离线期间 materialize Actor 或推进 spawnGeneration。
- EngagementCommand 的双方键固定为 `{spawnId, memberSlotId?, spawnGeneration}`；Roster Actor 使用稳定 `actorRecordId` 键域。processCommands 必须同时匹配 spawnId、member slot、generation 与当前 Lease，旧点击、Actor ID 复用、同槽重生和跨区残留命令均以结构化 `stale-generation|spawn-unloaded|region-changed` 拒绝。

### 多阵营 Encounter 与目标契约

- `encounterProfile` 新增 `teamSlots`、方向性 `relationMatrix`、`objectives` 与 `completionPolicy`。team slot 至少声明 `id`、`role: combatant | objective | observer`、可选 `coalitionId`、`countsForCompletion` 和 `rewardEligible`；运行时 Actor 另有 `active | defeated | surrendered | escaped | left` 参与状态。
- `observer` 不建立威胁表且默认不可被 Action 选中，也永不阻止 Encounter 结束；`objective` 可被保护或护送，但是否维持 Encounter 由目标声明决定；援军加入既有 team slot 或显式动态 slot，不靠"team 数量"改变胜负。estimator 的目标枚举与真实战斗同步尊重 role，禁止两者分叉。
- 首批目标 DSL 固定为 `eliminate`、`survive`、`protect`、`surrender`、`escape`、`timeout`，只接受稳定 team/coalition/tag/actor selector 和整数 tick 参数；特殊规则只能引用已注册、版本化且确定性的 objective handler，禁止内容内联函数。
- 每个固定 tick 按 `外部命令 → expire → periodic → movement/resource → resolve/reaction/commit → cleanup → phase/Variant → objective evaluation → AI` 执行。`Game.encounters.evaluateObjectives()` 是唯一自动结束入口，返回 `ongoing | success | failure | draw`；结束结果包含 `winningTeamIds[]`、`winningCoalitionIds[]`、逐目标结果、参与状态和奖励授权集合。旧消费者暂保留只读 `winnerTeamId` 投影：恰有一个获胜 team 时返回其 ID，否则为 `null`，不得再据此实现新逻辑；estimator 场景 `winnerTeamId === 'party'` 的判定继续成立（offline 的 failureRate 依赖它）。
- 现有双阵营 Profile 在编译时补成标准目标："玩家 coalition 至少一名 combatant 存活且所有敌对 combatant 均 defeated/surrendered/escaped"；该兼容投影必须保持现有 16 个 Encounter 的战斗时长、Boss phase 与首杀结果不变。
- 终止判定移位说明：objective evaluation 位于 AI 之前，而现行 `checkEnd` 在 AI 之后。因 AI 当 tick 提交的动作最早在下一 tick 的 resolve phase 生效，结束 tick 不得改变；唯一预期差异是最终 tick 不再产生 AI 派生事件。新旧差分夹具只比较结束 tick、胜负、Boss phase 与奖励授权，并显式豁免最终 tick 的 AI 事件。

### Engagement 固定 tick 事务

- `Game.combat` 维护独立于渲染帧的 50ms 整数 `combatClockTick`；即使当前没有 Encounter，只要存在外部战斗命令也继续推进。UI、世界点击和脚本只能向队列写入 `{commandId, requestedTick, sourceKey, targetKey, kind, openingAbilityId?}`；世界 `sourceKey/targetKey` 使用 `{spawnId, memberSlotId?, spawnGeneration}`，Roster 使用 `{actorRecordId}`。队列按 `requestedTick → stable(sourceKey) → stable(targetKey) → commandId` 排序。
- 时钟映射：`combatClockTick` 只用于命令排序与提交时点，Encounter 内部 tick 保持 0 起算，事件日志与黄金快照协议不变；两钟以"命令在其 requestedTick 之后的第一个 Encounter tick 前处理"衔接。长时间无战斗后收到首条命令时，命令钟直接跳齐当前时间、不做追帧补算；Encounter 追帧仍受 `maxCatchupTicks` 约束。
- `Game.engagement.processCommands(tick)` 在该 tick 的所有 Encounter phase 之前运行。重复 `commandId` 在当前会话幂等返回缓存结果；切区、回营、读档、Actor despawn 或 spawn generation 改变时，未提交命令以结构化原因取消，队列和幂等缓存均不入档并在世界重建时清空。同 tick 命令严格逐个处理：前一条完成 commit/rollback 后，后一条必须针对最新 `engagementRevision` 重新 prepare，禁止同时提交两个过期 Draft。
- prepare 在未挂入 `Game.actors/Game.encounters/Game.relations` 的 `EngagementDraft` 中无副作用构造候选 Variant 组件、Relation 记录、Encounter aggregate、team/objective membership、群体警戒、priority target 和 opening Action 静态资格；校验稳定键/generation、EngagementPolicy、保护状态、当前占用、leash/区域、Profile 和全部引用。中立非战斗 NPC 的 `onProvokedVariantId` 必须先完整编译并验证战斗能力。prepare 不分配正式 Encounter ID/事件 sequence，不调用公共 `start/join/setOverride/requestAction`，不消费 RNG，也不发布事件。
- prepare 成功返回不可变 `CommitPlan`：包含 `expectedRevision`、确定性正式 ID、全部新 aggregate/替换引用、只覆盖受影响键的 `mutationJournal`、Encounter seed/ordinal 候选和有序 `eventOutbox`。journal 记录旧值或“原先不存在”，不克隆全局 Registry/EventLog；outbox 此时只保存无 sequence 的事件草稿。任何无法在 commit 前穷尽验证的动态条件都必须变成 revision/键存在性前置断言，而不是把业务解析推迟到 commit。
- `Game.encounters.startAtomic(plan)` 只接受已编译 CommitPlan：先验证 `expectedRevision` 和所有前置断言，再用内部无事件 primitive 完成必要 Variant 引用替换、带 owner/scope 的 Relation 写入、Encounter 挂载、全体 join、team matrix、群体警戒和 priority target，最后提交 ordinal 并递增 revision。禁止复用会即时 log/emit 的现有公共 `start()`/`join()`。任何内部异常按 mutationJournal 逆序恢复，ordinal/revision/event sequence 保持原值，不留下 Relation、半加入 Actor、scheduler 或 RNG 消耗；失败只在回滚完成后通过 Encounter 外的命令结果流发布一个 `engagement:rejected`。
- Encounter seed 只由 worldSeed、regionId、稳定 spawnId/groupId、Population encounter ordinal 和 Profile ID 派生，不使用临时 Actor ID、时间戳或对象遍历顺序。ordinal 是 per-spawnId 的会话内成功 commit 计数，失败不递增、不同 spawnId 不互扰、读档从 1 重置；刷新后重放相同世界状态得到相同战斗序列是明确接受的行为。
- revision/前置断言通过后、正式 mutation 前，先为 outbox 分配从 1 开始的连续 sequence，并把完整 EventLog/nextSequence 装进尚未挂载的 Draft Encounter；commit 把这个已完整的 aggregate 与其他引用一并挂入，避免正式状态提交后再执行可能失败的 EventLog 组装。commit 完整成功后才按 `actor:variantChanged? → relation:changed → encounter:started → encounter:joined* → engagement:committed` 将同一批冻结事件交给 `Game.bus`。EventBus 监听器异常沿用现有隔离记录语义，不能回滚已提交事务；监听器因此永远看不到半成品。失败的 `engagement:rejected` 不属于尚未创建的 Encounter EventLog。
- outbox 发布完成后，在同一 combat tick 通过正式 `requestAction()` 尝试 opening Action。非法/不属于 Actor 的 ability 已在 prepare 阶段拒绝整个命令；合法 Action 因距离、GCD、资源或 busy 暂不能开始时，不回滚已成立的挑衅与 Encounter，而是记录尝试结果并保留 priority target，由正式移动/队列/AI 管线继续；成功时 `action:started` 使用正常 CombatEvent 顺序追加，禁止绕过射程、冷却或行动锁。

### Variant 转换事务

- `actorVariant` 可声明 `transitions`，每条边固定 `from/to`、允许的 `triggerId`、`timing: outOfEncounter | cleanup`、`activeAction: defer | cancel` 与 `persistence: none | actorRecord | worldSpawn`。未声明转换边、跨 archetype、战斗中移除 Vitals/Action 能力或改变 ActorRecord 身份的请求一律拒绝。
- 脱战转换立即进入 prepare/commit；战中转换只排入当前 Encounter cleanup phase。`defer` 等到 ActionState idle，`cancel` 必须复用正式 `cancelAction()` 退款，并按 action token 清除 scheduler、telegraph、预留资源和 queued Action，禁止把旧 ability 的延迟事件带入新 Blueprint。
- 固定迁移矩阵为：instance/record/spawn/transform/party/team/faction/controller/encounter 身份保持；HP 按旧最大生命比例映射并 clamp；同 ID Resource、Ability cooldown/group/charge 保留剩余 tick 并按新上限 clamp，新项取初始值、删除项丢弃；兼容 Status/Shield/Threat/Targeting 保留，带 `removeOnVariantChange` 或引用已失效组件的状态在 cleanup 中以确定顺序移除；Combo 仅在新 Blueprint 仍授予对应链时保留；AI、Presentation、Body、Interaction 与 Engagement 读取新 Blueprint。
- prepare 使用受影响 Actor 与相关 Encounter 的快照构造候选组件，重新应用 Trait、Status 和外部 Modifier ledger，并验证数值有限、组件前置条件、team/objective 能力、scheduler 引用和资源边界；快照限定为回滚所需最小集（受影响 Actor 组件、Encounter 的 team/threat/scheduler 引用与事件 sequence 水位），禁止克隆 eventLog 全量。commit 只允许一次引用替换；异常时恢复原快照且不得增加事件 sequence，成功后才发出一条包含 old/new Variant 和迁移摘要的 `actor:variantChanged`。
- `transitionVariant()` 本身不决定长期状态。Roster Actor 的持久 Variant 写入 ActorRecord；非 ephemeral 世界单位仅在转换边声明 `worldSpawn` 时写入 `world.social.spawnVariants[spawnId]`；普通怪、召唤物和 `persistence:none` 重生后回到 WorldSpawnProfile 声明的默认 Variant。存档永不保存 ActorInstance ID、Blueprint key、施法或冷却。
